# Plan: the views Caius can show

Builds the views half of `design/2026-11-03-views-and-background.md`: the ontology's "Where the
tools fall short" items 1–3 and decisions 1–6, with Shawn's four answers of 2026-11-03. Decisions
7–10 (background, notification, mini bar) are another branch's (`ktn-caius-background`). Branch
`ktn-caius-views-build`.

## Shape

### The one "over" figure

- **Arithmetic, pure.** `packages/caius/src/daily/load.ts`, no `t()`, no store, so the phone redraws
  a meter after a tap with the server's own arithmetic.
  - `liveMinutes(tasks)`: the minutes of live top-level work, a task with live sub-items counted
    through them, an unestimated one at `DEFAULT_ESTIMATE`. The same count `buildPlanView` makes
    for `capacity.areas`; a spec holds the two equal on the plan-read fixtures.
  - `dayLoad({ foundation, onDeck, growth, recharge }, { focus, growthTarget })` →
    `{ foundation: { minutes, focus, over, overMinutes }, onDeck: { minutes, overWith }, growth: { minutes, target, over }, recharge: { count } }`.
  - **Over** is `foundation.minutes > focus.max`; `overMinutes = minutes − focus.max`. On deck never
    counts; `onDeck.overWith` is how far over the day would be with it.
- **The focus figure** stays `focusFor(withBooked(read, plan))`: the Rhythm's Foundation target, or
  the meetings' leftover rounded to the quarter hour when that is less.
- **A calendar that failed** gives no meeting-aware figure. The day then reads the focus the steps
  stated (`#caiusFocus`) when there is one, else the Rhythm's target, and says `calendarFailed: true`.
  The steps keep not weighing the day without the calendar.
- **Where the figure goes.**
  - The day read (below), so `caius_show`, the steps and `caius_plan` share it.
  - `caius_plan` for a day: `capacity.target` and `capacity.areas.foundation.target` become the
    focus, `capacity.areas.growth.target` the Rhythm's Growth target, and `capacity.load` the
    `dayLoad` result. Today's card, the Over capacity notification and the desktop Plan tab follow
    without new logic, since they already read those fields.
  - The steps: `loadOf`, `nextAsks`, `planOffer`'s heavy check, `deckOffer`'s room and the
    Wind down apply's `load`. Each call site is listed in task 6 with what it becomes.

### The day read

- **A frame for a day, cheap.** `service.dayFrame(date)`: the Rhythm, the Context in force, the
  declined meetings and the calendar, with the capacity worked from them. The calendar comes from a
  fresh `inputsCache` entry for that day when there is one, else `readCalendar` alone, cached 15
  minutes like the inputs. Jira is never read for it, so Today doesn't wait on Jira.
  - Type `DayFrame = Pick<DayRead, "rhythm" | "context"> & { inputs: Pick<CaiusInputs, "calendar" | "capacity" | "errors"> }`.
    `withBooked`, `focusFor`, `failedCalendar`, `meetingsOf`, `drawnEvents` take a `DayFrame`; a
    `DayRead` is one.
  - The frame reads its notes under the lock and the calendar outside it, as `dayRead` does. The
    lock is a queue, not re-entrant, so no caller holds it when it calls `dayFrame` or `dayRead`.
- **`readDay(frame, plan, …)`** in new `apps/server/src/services/caius/day-read.ts`: the plan, the
  meetings (`meetingsOf`), the capacity (`capacityOf`'s figures), the load (`dayLoad`), Growth
  (`growthOf`), the layout (`workBlocks` with the brief's names: `groups`, `unplaced`), the slip
  count of each list and On deck task from the trail read, and the Context lines that bear on the day.
  `capacityOf`, `growthOf` and the load sentence are built from it, so the steps' sentence and the
  view's figure are one figure.

### The trail

- **`trails(store, now)`** in new `apps/server/src/services/caius/trail.ts`: every copy of every
  task, grouped by `copyKey` (the key `timesForwarded` uses), in order: its period, note, list item,
  state, and whether it moved on from there. `trailOf(item)` picks one item's; `slipsOf(items)`
  counts each item's moves off day notes.
- `staleItems` reads its counts from it, so Item, Slipping and Wind down's park all count the same.

### One ticket, several days

- **`readTicket(deps, key)`** in `inputs/jira.ts`: the issue (key, summary, status, days in that
  status, assignee, done) and its last comment and asks, with the same timeout and error words as
  `readJira`. `service.ticket(key)` caches it 15 minutes. Unconfigured Jira answers `not_configured`.
- **`readDays(from, count)`** in `day-read.ts`: `readDay` for each day (one `dayFrame` each) and
  the week's `readPlan`, plans read under one lock. A future day with no note has its meetings and
  nothing else. The Week row: the week note's live items not yet on a day, and the week's Foundation
  minutes (its own items plus its days' lists) against the week target, 720–900.

### The two writes

- **Place a task in its day**: `caius_place`, `{ items: [{ noteId, listItemId, block?, onDeck?, before?, after? }] }`.
  - `block` is `morning`, `afternoon` or `evening`; `onDeck: true` puts it On deck, `false` onto
    the list; `before`/`after` an item of the target list. At least one of `block`, `onDeck`,
    `before`, `after`. A heading that is missing is made, as `caius_add` makes it.
  - The item keeps its words, state, sub-items and id. It stays on its note: a move to another
    day is `caius_forward`.
  - `placeInDay(html, id, place)` in `plan-html.ts`: lift the `li` (as `takeOnDeck` lifts it), then
    `placeTask` with a position. `placeTasks(api, reqs)` in `plan.ts`, shaped like `setAreas`: the
    note's items applied in order to one HTML, one compare-and-swap `putContent`, `edited` on a race.
- **Set an estimate**: `caius_set_estimate`, `{ items: [{ noteId, listItemId, minutes }] }`.
  - Writes the `~` token where `parseLine` reads it, replacing one already there: before a trailing
    `!` marker and after the `_from …_` italics a forwarded copy ends with (`scanTokens` reads tokens
    from the end, so one before the italics would be prose). `minutes` is 5 to 600.
  - A task with live sub-items counts through them, so its own estimate changes nothing: skipped
    `has_subitems`, with the words "set the estimates of its sub-items".
  - `setTaskEstimate(html, id, minutes)` in `plan-html.ts`, `setEstimates` in `plan.ts`, shaped like
    `setAreas`.
- Both in `service.ts` through `unlessStale` and `withBlobIds`, schemas in `schemas.ts`, and tool
  words in `tools.ts` as one block after `caius_set_area`. No `/api/caius/` route in v1.

### `caius_show`

- `{ view: "day" | "days" | "item" | "slipping", date?, from?, count?, item?, key?, area?, period? }`.
  Read only. `item` is `{ noteId, listItemId }`; `key` a ticket key.
- Its result: `{ view, title, data, sentence }`. `data` is the view's (below); `sentence` is the
  figures in one line, for a client that draws no views (the desktop chat). Every task row carries
  `noteId` and `listItemId`, a ticket its key. Days and Slipping go through `fitted`, with their rows
  capped.
- The readers live in new `apps/server/src/services/caius/views.ts`:
  - **day**: `readDay` for `date`, with `area` (or the area that is over) as `openOn`.
  - **days**: `readDays(from, count)`, `count` 2 to 7.
  - **item**: the task (from the day it is on, or `caius_open`), its trail, `originOf`, and for a
    key the ticket, the Context lines naming it and its dispositions (dismissed, finished, not
    today). A key with no task: the ticket alone.
  - **slipping**: `caius_open`'s live tasks with 2 moves or more, longest trail first, then the
    overdue lane's count by age (under a week, 1–2 weeks, older).

### The phone

- **`lib/views.ts`**: `viewOf(call)` reads a `caius_show` result as `stepOf` reads a step (it uses
  `parseResult`, exported from `lib/chat.ts`); the view types; `viewReply(view, answers)` (the
  sentences) and `viewPicks(view, answers)` (the pill rows); `redraw(view, answers)` applies the
  pending taps to the rows and recomputes the meters with `dayLoad`.
- **Taps gather, then send.** A view reports `{ sentences, picks, total }` like `StepCard`, through
  `report(id, answer)` and `live` props, never the `Chat` type. A view with no taps reports nothing,
  so the pill never sends "All as proposed" for a view.
- **Sentences** Caius maps onto tools, in the step cards' form (`itemsReply`: the item's words in
  quotes, then its fate): `"Garage shelf" goes in the afternoon`, `"The ballot" goes On deck`,
  `"Garage shelf" goes on Mon 9 Nov's On deck`, `"ZAP-2611 review" is 30 minutes`, `"The ballot" is
  Growth`, `"The ballot": drop it: not needed`, `Take ZAP-2640 today`. The view's rows carry their
  `noteId`, `listItemId` and a `ref` (`withRefs`, prefix `v`), so Caius finds each item in the
  `caius_show` result it already has.
- **Item types**, `components/`: `TaskRow` gains the Important mark, the clock, the slip count
  from 2 and a ticket chip; `AreaMeter` (lifted from Today's `CapacityRow`, with the pending
  result as a ghost); `TicketCard`; `ContextLine`; `FateMenu`, the sheet `FateList` opens today,
  grown into the one control: Done; Morning, Afternoon, Evening; On deck / onto the list; next
  workday; a day; the week; Park (Slipping); Drop with a reason; estimate 15 m, 30 m, 1 h, 2 h;
  area. `FateList` keeps its own options and uses `FateMenu` to draw them.
- **`screens/views/`**: `DayView.tsx`, `DaysView.tsx`, `ItemView.tsx`, `SlippingView.tsx`, each
  with its CSS file, and `ViewCard.tsx`, which picks one by `view`. `Chat.tsx` gains one line in
  `AssistantBlocks` beside the step cards: a `caius_show` call draws its `ViewCard`.
- The Day view's timeline is `renderDayTerrain` with `layoutGroups` on the day read's groups, as
  Today draws it.

### The skill sheet

## Tasks

Server tasks touch `daily.ts`, `service.ts`, `schemas.ts` and `tools.ts`, so they run one at a
time, in order. Phone tasks 10–12 run one at a time after task 1, and can run beside the server
tasks from task 7 on; they need the result shapes from task 9, so 11–12 start after it. Each task
ends in one commit, `caius: …`, with a body that says why.

Test commands:
- caius: `cd packages/caius && corepack pnpm exec vitest run src/<path>`
- server: `cd apps/server && corepack pnpm exec vitest run src/services/caius/<file>`
- phone: `cd apps/caius-app && corepack pnpm exec vitest run <file>`
- client: `cd apps/client && corepack pnpm exec vitest run src/widgets/sidebar/plan`
