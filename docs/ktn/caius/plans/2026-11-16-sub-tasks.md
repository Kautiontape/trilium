# Plan: sub-tasks

Builds Part 2 of `design/2026-11-16-subtasks-reword-flip.md` (sub-tasks) and Part 1 item 7 (parents
matched by row, not text). Branch `ktn-caius-nesting`, one PR against `ktn`.

## Spike (done 2026-11-16)

A nest written over ETAPI in CKEditor's own shape survives the web editor: a parent with two moved
items, then an edit to another line and to a sub-item, each saved. Every `data-list-item-id`, the
nesting and the states came back as written; the editor only added ids to the plain Meetings and
Context bullets. `caius_plan` reads `parent` and `parentListItemId` for both sub-items. The shape the
writes use, the sub-list inside the parent's `<li>` after its `</label>`:

```html
<li data-list-item-id="P"><label class="todo-list__label"><input type="checkbox" disabled="disabled"><span
class="todo-list__label__description">09:30 Standup ~15m</span></label><ul class="todo-list"><li
data-list-item-id="A">…</li><li data-list-item-id="B">…</li></ul></li>
```

## Settled while planning

- **One level.** Nesting under a sub-item is `too_deep`, and so is moving a task that has sub-items of
  its own under another (it would make two levels). A hand-made deeper nest is still read.
- **A parent without a list item id** is found by row: the scanner's `parentRowid` inside one note
  (`plan-read.ts`), and in the pure helpers the nearest earlier task of the same note whose words are
  the sub-item's `parent`. Two tasks with the same words no longer share sub-items.
- **The meeting parent** is read from the day note's Meetings lines (`plan.meetings`, `HH:MM Title`),
  which Plan my day writes from the calendar, so the phone and the desktop redraw the same figure
  from the plan alone. A day whose Meetings block is empty has no meeting parent.
- **Project runs** name a task's project by its "from" link when that names a note outside the
  Journal, else by the `<project title>: ` prefix an accepted project pick is written with. Accept
  writes no link today, and this plan leaves that alone.
- **Asks in a nest** that are candidates not yet taken are taken by the nest (a yes to "put the 4
  answers under standup" is a yes to the answers).
- **localStorage** holds which parents are open, per device, as the design says (the nudge bar keeps
  its dismissal the same way).

### 2. Count a parent by its own estimate, else its sub-items

Files: `load.ts` (+ spec), `plan-read.ts` (+ spec).

- One pure function in `load.ts` decides every figure: `countUnits(tasks, { meetings? })` →
  `{ task, minutes, estimated, unestimated }[]`, one entry per **unit**: a live, non-empty task
  whose parent (by `parentsOf`) is not live. A unit's minutes:
  - a task with no live sub-items: its estimate, else `DEFAULT_ESTIMATE`;
  - a parent with an estimate of its own: that estimate, whatever is under it;
  - a parent without one: the sum of its live sub-items, each counted by these same rules;
  - a **meeting parent** (a task with live sub-items whose `at` equals the clock that starts one of
    `meetings`, the `HH:MM …` Meetings lines): 0, its sub-items included. A pinned task with no
    sub-items counts as before.
  - `estimated`/`unestimated`: how many of the unit's leaves fell back to the default (a parent
    with its own estimate has 1 estimated, 0 unestimated; a meeting parent 0 and 0).
- `liveMinutes(tasks, area?, opts?)` sums `countUnits`, a unit in its own area. Export
  `unitMinutes(task, tasks, opts?)` for one row (the phone's and the brief's hills).
- `plan-read.ts` builds `plannedMinutes`, `estimatedCount`, `unestimatedCount`, `totalMinutes`,
  `eveningMinutes`, `areas` and `onDeckMinutes` from `countUnits`, `meetings: doc.meetings`.
- A sub-item with no area marker takes its parent's area (`planTasks`: its area is the parent's
  unless its own text is marked).
- Failing tests first (the design's list): parent estimate wins; no estimate sums the live
  sub-items at 30 each; a meeting parent adds 0; a pinned non-meeting parent follows the rule; a
  sub-item of a 🌱 parent counts as Growth; a done parent's open sub-item counts on its own.
  Update existing expectations the rule changes (the "Learn it ~45m" fixture) and say which in the
  commit body.
- Done: package suites for `daily/load` and `trilium/plan-read` green.

### 3. The nesting writes, as HTML

Files: new `packages/caius/src/trilium/nest-html.ts` (+ `nest-html.spec.ts`). Reuse `html-util.ts`
(`findItem`, `elements`, `apply`, `isTask`, `itemState`, `inProseSection`, `inCriticalAside`,
`sectionOf`) and `plan-html.ts`'s `itemMarkup`; don't edit `plan-html.ts`.

- `addUnder(html, markup, parentId)`: `markup` becomes the last sub-item of `parentId`, in its
  sub-list, made right before the parent's `</li>` when it has none.
- `nestUnder(html, id, parentId, states)`: the item (live, top-level, no sub-items of its own)
  leaves its list (the list goes when emptied) and becomes the parent's last sub-item.
- `nestNew(html, ids, parentMarkup, states)`: a new parent at the first item's place, with the
  items under it in the order given.
- `liftOut(html, id)`: a sub-item moves to right after its parent in the parent's list; the
  sub-list goes when emptied.
- Refusals `{ ok: false, reason, detail }`: `not_found`; `not_live`; `too_deep` (the target is a
  sub-item, or the item has sub-items); `bad_request` (an item under itself, an item in Suggested,
  a Meetings or Context item, an Important item nested outside the Important block, `liftOut` on a
  top-level item).
- Every result is spliced into the original string; ids, states and other markup stay byte for
  byte. The spec asserts the exact output shape of the spike (above) and that parsing it back
  (`planTasks`) gives the expected `parentListItemId`s.

### 5. Nest through `addTasks` and `placeTasks`

Files: `plan.ts` (+ `plan.spec.ts`).

- `AddRequest.under`: a list item id in the target note. The new task becomes its last sub-item
  (`addUnder`); `section`/`critical`/`onDeck` are not needed with it. An id in another note:
  skipped `other_note`; in no note: `not_found`.
- `PlaceRequest.under`: an id (`nestUnder`) or `{ text, est?, area? }`. Items of one note with
  the same `under` object are nested together by `nestNew` in request order; the new parent's text
  gets `~est` and the area marker (`withArea`). `PlaceRequest.out: true` runs `liftOut`. The
  shape check (`placeProblem` or a new one beside it) takes exactly one of block, onDeck,
  before/after, under or out. `other_note` as for add (look the id up across the Journal docs).
- Results: `moved`, with `parentListItemId` naming the parent (new or given).
- Failing tests first: add under; place under an id; place two items under a new parent with
  est and area; out; `too_deep`; `other_note`; a re-run of under/out is `unchanged`.
